copies, checked in so the output can be read without cloning, seeding, and

## Regenerating them

Flux (the `2026-07 -> 2026-08` comparison is the last period pair in the seeded
dataset, so a bare `run_flux.py` produces it):

```bash
python data/seed_flux.py      # 20 months of summary + transaction CSVs
python run_flux.py --replay   # walk every period oldest-first so memory accumulates
# or just this one comparison, against whatever memory already exists:
python run_flux.py 2026-08
```

AP:

```bash
python data/seed.py
python run_demo.py
```

The `9cc000e5` / `38e95103` suffixes are per-run ids (`uuid4().hex[:8]`), so a
re-run writes the same content under a different filename. The narrative prose
also comes from the model, so it is not byte-identical run to run; the numbers,
driver tables, priorities, and owners are computed deterministically and are.

## Notes on the artifacts

**Insurance ranks last here, deliberately.** It is 0% traced to subledger detail
in every period, and an earlier version of `actions.gap_priority` judged on
coverage alone — so a $5,000 accrual that has not moved in twenty periods came
back P1 every month and topped this table, above a $96,000 revenue swing. Gap
priority now scales with the money behind the gap, so it sits at P2 below the
real movers. The same account correctly returns to P1 in `2026-05`, the month its
gap is genuinely $30,000.

**The memory-graph excerpt.** The full file is gitignored (it is state, not
source) and is rewritten by `memory.save_graph` on every run. The four edges
kept here are the ones worth reading:

- `5000::CloudBeam Compute` — the recurring hosting overrun, fired in `2026-06`
  and `2026-08`. This is the edge behind a headline reading "recurring" rather
  than "new".
- `5000::NimbusHost Cloud` — the same account's second vendor, six periods deep.
- `6000::TechConf Expo` — the seasonal case: the sponsorship lands in `2025-08`
  and again in `2026-08`, which is what a year-over-year seasonality read is
  built on.
- `4000::ENT-01` (Globex Corp) — the flagship revenue driver.

Each `periods` entry stores that driver's `delta` and `contribution_share` for
the period. `memory.recall()` reads these edges by exact `account::driver` key.

**Why there is no `2026-09` in this excerpt.** The seeded dataset ends at
`2026-08`. A local graph may still carry `2026-09` edges — along with edges
keyed `<account>::None` and customers keyed by *name* beside the same customers
keyed by id (`4000::Globex Corp` vs `4000::ENT-01`). All of that is residue from
a since-removed ad-hoc CSV upload path, whose uploads had no `customer_id`
column, so `slicer.slice_drivers` grouped on a null or on the name. It is not
reproducible from the seeded data — every seeded row carries both a
`customer_id` and a `vendor` — and those edges are excluded here.

`slice_drivers` now coalesces a null grouping key to an explicit
`(unattributed)` bucket rather than letting it become a driver named `None`. A
bucket rather than a filter, so the driver shares still sum to the account
delta: a subledger row with no counterparty on it is still real money, and
hiding it would quietly break the arithmetic. On the seeded dataset this changes
nothing — there are no null keys to coalesce.

**A defect in the flagship brief's executive summary.** The summary paragraph
renders the 71% *concentration share* ("three customers account for 71% of the
increase") as "a 71% increase". The per-account finding headline directly below
it states it correctly. The synthesis prompt hands the model both a percentage
delta and a concentration share and it conflated them. Left as-is rather than
hand-edited, because the artifact should be what the system actually produced.
